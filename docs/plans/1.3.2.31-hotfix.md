## Context

In 1.3.2.30 a Ritual scan was dropped silently: the capture showed and the message bar was empty, with no confirmation. The user reports it was a new page. The user's rule stands: **the roll count is the tracker**. Same rolls-left as the map's last saved page means a duplicate, discarded. Rewards are not compared, because rewards can legitimately repeat. The rule must **reset on every map**: a page must never be dropped because of a previous map's roll count, and once **+ New map** is pressed the previous map is locked.

Code facts:
- The check (`_ritual_read` → `logger.last_ritual_rerolls(map_id)`) reads only the current map's commits.
- Ritual saves only reach the current map.
- One leak: while the next-map marker is set (`pending_new_map`, map finished but next not started), `current_map_id` is still the **finished** map, so a scan then is compared with the old map's pages.
- Dropped scans give no feedback, so the user can't see what a drop matched.

The 1.3.2.31 hotfix also carries the finished, uncommitted work below.

## 1. Rolls safeguard: only ever the current map (priority 1)

- **A scan belongs only to the map the app shows when the scan is taken.** It is compared only with that map's saved pages and logged only to that map, never to a map that doesn't exist yet. **+ New map** is the only thing that moves to the next map.
- In `_ritual_read` (`PoE2_Data_Logger/ui/native_desktop.py`), compare and save using the capture's map, `capture["context"]["_capture_map_id"]`, i.e. the current map at capture.
  - If the map changed before the result arrived, the existing context check refuses the scan with "Scan again"; it is neither dropped silently nor saved elsewhere.
- `logger.last_ritual_rerolls(map_id)` (`core/logger_store.py`) keeps its meaning: only `commits` with `kind='Ritual' AND map_id=?`. Have it also return the page number and Scan Commit # of that page, for the confirmation.
- The previous map is locked after **+ New map**: no scan can be compared with it or written to it. Covered by the tests below.

## 2. Confirmation for every Ritual scan outcome

- Repeat dropped (rename `_discard_repeat_ritual_scan` → `_end_ritual_scan_quietly`, now taking a message):
  - show "✓ Already saved: M0172 page 1 had 4 rolls left (Scan Commit #N)." in `review_summary` (role `success`) and `note()`;
  - show nothing else: no review, no window, no input;
  - the capture preview stays, with this message under it.
- Page whose rewards are all deferred and that has no readable counters: "✓ Ritual page read: every reward is deferred, nothing new to log."
- Saved and held pages keep their existing messages.

## 3. Already done (uncommitted), ships too, with the user's corrections

- Rite map name read from the title above "Biome:", not the FPS counter.
  - **Biome is never used to identify a stage.** A Rite can have several maps on one biome, and each stays its own stage.
  - A rescan replaces a stage only when map name **and** every modifier match. Two maps with the same name but different modifiers stay two stages (existing two-Necropolis test).
  - Add a test: two different maps sharing a biome, e.g. Savannah and Seepage (both Grass), stay two stages.
- **+ New map** sets Biome / City type from the stage it plays, shown in the BIOME / CITY TYPE pickers and the status message and correctable there; the queue table shows "Map · Biome".
  - **City maps take the Atlas secondary biome.** The tooltip's "Faridun City" sets City type Faridun, then `_atlas_city_biome` (`core/logger_store.py`) applies the Atlas keystone's "also counts as" biome (Faridun → Desert/Mountain, Ezomyte → Grass/Swamp, Vaal → Forest…). With no keystone allocated, Biome stays None.
  - Add a test using the Atlas fixtures in `tests/test_atlas_biome_sync.py` (`self.atlas()` with a city choice). A Rite stage of a Faridun City map with the keystone allocated → after **+ New map**, City type is Faridun **and** Biome is that Atlas biome, both visible in the header pickers.

## Tests (`tests/test_ritual_repeat_pages.py` + 100-map session)

- Same rolls on the same map → dropped, showing the confirmation that names the map, page, rolls and Scan Commit #; no review.
- After **+ New map**, a page with the same rolls as the previous map's last page → saved to the new current map; the previous map's pages and commits are unchanged.
- A scan whose result arrives after **+ New map** (captured on the old map) → refused with "Scan again", never saved to either map.
- Unread rolls are never dropped; Undo of the saved page re-allows its rolls.
- 100-map session: every map's first page uses the previous map's last roll count and must save; page 2's repeat is still dropped.
